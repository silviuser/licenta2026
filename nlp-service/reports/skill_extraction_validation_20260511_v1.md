## 6 — Failure analysis

**Top false-positive patterns** (20 FPs total across 6 CVs):

1. **Pronoun `It` → "computer technology"** (3 CVs: Silviu, canva, 14-03). The bigram-level matcher accepts the case-insensitive token `It` as the ESCO abbreviation "IT". Cheap fix: enforce an upper-case constraint or POS filter (the abbreviation is never a determiner/pronoun in real corpora).
2. **`banking` → "economics"** (3 CVs: Silviu, canva, 14-03). The "Bank Management System" project — a database exercise — is matched to ESCO's broad *economics* concept. The surface `banking` is genuine but the ESCO mapping is too aggressive a generalisation; mitigations include lowering the confidence prior for very broad concepts or requiring multi-surface evidence.
3. **`security` → "securities"** (3 CVs: Silviu, canva, 14-03). Plural/singular collision between *computer security* and *financial securities*. The Romanian/English language overlay does not disambiguate by domain.
4. **`integrity` → "morality"** (3 CVs: Silviu, canva, 14-03). The phrase is always "data integrity" — a technical attribute — but matched to ESCO's *morality* concept. Same class of error as #3: same surface across two ESCO concepts, no disambiguation.
5. **`designing` / `design` → "think creatively"** (3 CVs: Silviu, canva, 14-03). In every occurrence the verb modifies *database design* — a technical, not creative, activity.
6. **`Visual Studio` / `.NET` → "Visual Basic"** (Silviu CV12, 14-03 CV12). The IDE and the .NET framework are conflated with the Visual Basic language because of shared substrings.
7. **`logical` → "logic"** (Silviu CV6). Substring match on the adjective in "logical database design".
8. **`ML` → "ML (computer programming language)"** (two_column CV5). The abbreviation `ML` for *Machine Learning* collides with ML the functional programming language; both senses fire simultaneously (the correct *machine learning* sense fired too, but the incorrect ML-the-language sense also fired).
9. **`communication` → "communication" (soft skill)** (Silviu CV13). The CV says "secure communication protocols" — a technical concept — but is matched to the generic soft skill.
10. **`document management` → "document management"** (Silviu CV4). Surface matches the ESCO concept verbatim, but the CV mention is incidental ("efficient document management" in a project description), not a claimed candidate skill.

The common pattern: **ESCO matching is purely lexical / lemma-based; it cannot exploit the surrounding sentence to disambiguate between technical and non-technical senses of the same surface form.**

**Top false-negative patterns** (55 FNs total across 6 CVs):

1. **Concrete frameworks/tools not surfaced** — Docker, Kubernetes, TensorFlow, React.js, Node.js, .NET, IntelliJ IDEA, RESTful APIs, Oracle Database, PL/SQL, Microsoft Office. Many of these *do* exist in the ESCO bundle; the failure is in the surface-form index (e.g. `Node.js`, `React.js` are not normalised). A literal-string matcher needs every alias enumerated.
2. **C / C++ never surfaced** — `C/C++` (slash-joined) is not segmented by the tokenizer. Appears in 4 of 6 CVs. Highest-impact single fix: a `C/C++` → `[C, C++]` aliasing rule.
3. **Compound multi-word skills** — Object-oriented programming (OOP), Data Structures, Memory Management, Network Security, Cryptography, Secure Coding, Real-time Concepts, Embedded Systems, Database Design, Microservices, Backend development, Full-stack web development. Even when the literal multi-word string is present in the CV, the matcher prefers to fire on single-token surfaces from the same sentence (`SQL`, `Java`) rather than the compound. A phrase-priority pass would recover most of these.
4. **Language section ignored** — `B2 - english level`, `English (fluent)`, `Romanian (native)` are not picked up because the matcher only triggers on bare `English` (and only when capitalised inside a SKILLS section, never inside a LANGUAGES section). The section classifier should treat *languages* as a first-class section type.
5. **Roles / disciplines treated as headings, not skills** — Data Scientist, Data Analyst, Software Engineering, AI, Mathematics — extracted as job titles or education headings but never re-emitted as candidate skills.

These FN classes are the explicit motivation for **Module 3** (semantic / contextual encoder): a sentence-bi-encoder over ESCO concept embeddings should (a) recover compound and synonym-based matches that the literal matcher misses, and (b) suppress the matched-but-out-of-context FPs catalogued above by scoring contextual similarity rather than substring overlap.

## 7 — Conclusions

The labelled metrics describe a **high-precision-when-it-fires, very-low-recall** literal matcher:

- **Precision** is macro **0.737** (micro 0.604). The matcher is fairly trustworthy when it produces a single-token, exact-surface match (`Python`, `Java`, `SQL`, `C#`) — every TP in the corpus is a literal surface match.
- **Recall** is macro **0.358** (micro 0.368). The matcher misses roughly two thirds of the candidate's real skills, predominantly because (a) compound phrases lose to single-token matches, (b) common frameworks lack surface-form aliases, and (c) the language section is structurally ignored.
- **F1** is **0.463** macro / **0.457** micro — almost identical, which means the per-CV variance is moderate and the recall bottleneck is systematic rather than CV-specific.

The error breakdown clearly separates into two classes that Module 3 must address:

1. **Disambiguation FPs** (banking→economics, integrity→morality, security→securities, designing→think creatively, `It`→IT, .NET→Visual Basic). A contextual encoder that scores ESCO concepts against the surrounding sentence — rather than against a lemma — will down-rank these matches when the surrounding context is technical/CS rather than economic/financial/ethical/creative.
2. **Conceptual FNs** (compound phrases, framework aliases, Docker/Kubernetes/TensorFlow, language section). A semantic retriever over ESCO concept embeddings will surface these even without exact-surface coverage, provided the section classifier passes the language section through.

**Module 2 is therefore validated as a strong-precision recall floor** — every TP from Module 2 is a low-risk signal worth keeping — and Module 3 will be measured against the same fixture set on its ability to (a) raise recall toward parity with precision and (b) eliminate the systematic FP families catalogued above.
